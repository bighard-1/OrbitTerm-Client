# Android / Windows 排队删除与远端墓碑证据收敛（2026-10-15）

本专项接续 Apple 旧 `HTTP 409` 删除队列收敛。范围仅限源码、自动化与隔离 Android 模拟器；没有操作测试账户资产、服务端或线上部署。本行所在客户端提交为源码候选，不能当作五端完整验收。

## 原始缺口与修复

- Windows：原删除重试每次生成新操作 ID 和新向量钟；拉取同 ID 墓碑时直接清除本机待删除意图，未证明云端墓碑覆盖本次请求。现于网络请求前将操作 ID 与请求向量钟写入 DPAPI 保护的同步状态，重试复用；远端状态仅在同 ID、`deleted`/`purged`、正数服务端修订及严格向量钟覆盖时确认排队删除。旧队列无请求钟时不静默确认，下一次有本地有效基线时重新生成并持久化请求。缺失元数据但仍有排队删除时也不当作纯本机删除成功。
- Android：原 outbox 只有操作 ID，没有首次请求钟；重试会从可变同步元数据重新计算钟，且拉到远端墓碑时只更新元数据，不清除有充分证据的旧删除队列。现 Room 12→13 增加可空请求钟，用户发起软删时在同一数据库事务内捕获；旧队列首次投递前用操作 ID 条件写入并重读，重试发相同钟。拉取墓碑只在同 ID、墓碑态、正数修订、严格向量钟覆盖时用操作 ID 条件清除队列；无证据则保留。迁移不伪造旧队列证明。
- 两端均不把资产名称、响应正文、密码、令牌或完整地址写入判定字段。Android 活动清单与本机元数据同时缺席时，也不再把账户同步资产的排队删除当成“从未上云”直接清除，因为活动清单可能省略已删或无法解密的记录。较旧且已失去有效基线的排队删除、以及极短时间内新建后又删除而尚未上云的资产，可能保持阻断；需要后续可靠的云端缺席证明或人工安全处理。这是保守的未关闭项，不得以本次源码修复声称旧队列全部自动归零。

## 2026-10-15 Windows 到 K60 反向失败及修复候选

Windows 原生旧 QA 仅新建虚构 `ot-win-cross-20261015`（文档保留地址段、占位账号/凭据，不连接主机），手动同步后个人中心显示上传 1 项；K60 独立 QA 在“未分组”显示该项。Windows 对此唯一项普通删除：确认框虽只显示目标及本机清理文案，源码实际先安全排入账户墓碑，再移除本机资产和凭据。Windows 随后个人中心显示“删除墓碑 1 项”。**反向失败结果**：K60 同步后活动列表仍显示该项，并报“已同步 4 项资产、0 条命令片段；1 项已停止后台重试”；同一 K60 的云端“最近删除”却明确列出此项。故不能称 Windows→K60 墓碑矩阵通过，也不能凭 Windows 上传计数代替 Android 本机消失。受阻项身份/固定错误码当时无安全可见入口，不宣称已证明它一定属于此项；没有点“丢弃受阻项目”。

源码审查确认 Android `pullAndApplyAssets` 旧路径在导入远端活动资产时只写入资产/凭据，不写入该远端修订与安全影子。若另一设备很快删除，而本机下一次处理先运行“无基线本机资产登记”，可能误排队 UPSERT；云端已删资产的有效本地编辑本就应保留冲突，不能粗暴清空所有队列。修复候选统一复用 `applyRemoteAsset`，使首次导入流程同时保存资产、凭据、远端基线；旧设备已产生的 UPSERT 仅在已删墓碑可解密、身份匹配且**本机所有可比较字段与凭据均与墓碑原始内容完全一致**时才清理，缺密文、已彻底删除、身份不符、凭据缺失或任何本地改动均不自动丢弃。该源码风险与本次失败相容，但因旧受阻项身份未读到，不称已确认唯一根因。

首次误调用并不存在的 `:data:testQaUnitTest` 导致 Gradle 退出 1；纠正为 `:data:testDebugUnitTest :app:testQaUnitTest :app:assembleQa` 后成功（281 任务，49 执行、232 up-to-date）。完整 `scripts/security/check_android_release_gates.sh` 通过（417 任务，49 执行、368 up-to-date，含跨端源码对照及 Release/Smoke 构建）。新 arm64 独立 QA APK SHA-256 `84583fd8937cf8d14f122bfbb9beefbdb352c4c69c28b367cdefe8f482b8b5b4`，调试签名；`adb install -r` 到 K60 成功，保留数据与正式版。安装后主密码解锁，活动列表已无 Windows 测试项；初次仍显示受阻 1 项，下一次手动同步变为“同步完成：已同步 4 项资产、0 条命令片段”，活动列表保持无该项。**安装重启与同步之间的时序存在混淆**，这不是全新资产在不重启 Android 应用时立即消失的证据，也没有安全地识别旧受阻项身份。

Windows 同步资产删除确认框误写“仅从当前 Windows 设备删除”，而同一操作已上传墓碑，是会影响用户预期的交互缺陷。Windows 源码候选现按同步/仅本机范围分别提示：同步资产会先记录墓碑、在后续双向同步传播到其他设备，记录失败则本机保留；仅本机资产不会影响其他设备。此文案**尚未构建/安装到 Windows 真机**，原旧包提示失败保留。试图再新建第二个虚构项做纯在线反向复测时，Mac RDP 键盘/IME 把名称与主机字段串位；发现后以 Escape 取消，未保存或修改任何额外资产。后续需可靠输入渠道重新做不重启双同步，且补 Windows 离线删除/重启队列与 Android 真正本地编辑冲突。五端同版及新服务端隔离契约仍未验收。

## Windows 首次解锁遇到空墓碑的源码收敛

只读对照服务端仓库：`PurgeAsset` 把密文清空，增量拉取仍返回 `purged` 最小墓碑；Windows 旧 `ReadOnlyEncryptedConfigUnlockVerifier` 从游标 0 只取首页，不分状态即把空 Base64 传给旧版解密，空输入会抛 `ArgumentException`，而调用方把此类异常合并为泛化“同步服务暂时无法完成验证”。若首页只有已彻底删除记录，还会错误地把“无可验证密文”当成“主密码错误”；若有效记录在下一页也完全看不到。这是**已确认的源码/契约缺口**，与本机首轮症状相符；但没有读取该测试账户的未脱敏响应，所以不宣称已证明本次唯一运行时根因。

Windows 源码候选现跳过 `purged` 和空密文记录，以只读分页查找加密证明；有密文却均无法解密时维持错误密码，完全无密文返回需要可验证配置，游标不前进及超过 100 页时安全失败，不放开同步。新增空墓碑、跨页与不前进游标回归用例；本节记账时 CI、隔离 GUI、新包实机尚未完成。后续固定新构建身份重试同一账户，再决定是否还有其他失败阶段；不以源码推断替代 Windows 原生验收。
