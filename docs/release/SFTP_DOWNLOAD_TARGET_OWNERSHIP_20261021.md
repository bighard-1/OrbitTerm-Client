# SFTP 下载目标所有权边界（2026-10-21）

## 原问题与影响范围

共享 Rust 核心的 `download_file_create_new_cancellable` 先以 `create_new` 打开目标；旧实现不论该步骤是否成功，只要整个下载返回错误，就对目标路径执行 `remove_file`。若上层规划路径后，另一个本机进程先创建同名文件，`create_new` 正确拒绝覆盖，但旧错误清理随后可能删掉**并非本次下载创建**的文件。这是源码可证明的竞态风险，不是已经观察到用户文件丢失；不能把之前“取消后无残留”的真机结果解释为这个边界已通过。

`7dfe8d7` 将创建与失败清理收束到同一辅助函数：只有 `create_new` 成功后才可能清理；打开远端或本机创建失败直接返回，不删目标。下载读/写/取消失败仍清理本次创建的部分文件。此修复作用于共用该 Rust checked SFTP 下载路径的客户端；不改变 Android SAF 文档提供方的独立清理策略。

同轮进一步审查发现上传侧对应问题：远端随机临时名以 `CREATE | EXCLUDE` 排他创建，旧代码在该创建失败后仍尝试删除临时路径。`b54adb9` 改为仅在排他创建成功后才允许失败清理；临时名随机并不能代替所有权证明。这里同样只确定源码风险，未观察到真实远端文件被误删。

## 验证与边界

- **源码/自动化**：新增两个本机文件回归：已存在的目标使 `create_new` 失败时，原内容字节不变；新建目标写入部分内容后发生取消错误时，目标消失。定向 6/6；包含上传条件修复后的 `orbit-core` 全库 315 通过、0 失败、2 个需独立 OpenSSH 夹具的测试按原配置忽略；`cargo clippy --lib --locked -- -D warnings` 通过，`cargo fmt --check` 通过。远端上传排他创建碰撞**尚无模拟服务器/真机专项回归**，不能以本机文件测试代替。远端固定提交门禁仍待执行/核对，不沿用上一提交结果。
- **隔离 GUI**：本轮未启动桌面或移动端 GUI。自动化只覆盖本机文件操作与核心编译，未模拟真实 SFTP 网络。
- **真实设备**：本轮未重装 Windows 10、K60 或其他三端 QA。此前 Windows `b921c58` 在默认监控下两轮暂停/取消后，专用目录各为 0 文件；此前 K60 受保护 QA 对系统文档提供方取消后清理新建空文件通过。两者都是旧候选的正向结果；Windows 旧包的“部分失败”、目录弹窗阻断、监控误断线和 K60 旧包残留 0 字节失败仍按原日志保留，详见 [Windows SFTP 专项](WINDOWS_SFTP_PAUSE_CANCEL_20261020.md) 与 [K60 SFTP 专项](ANDROID_SFTP_DEVICE_20261020.md)。
- **五端完整验收**：未完成。Windows 后续用新固定签名候选，在仅含虚构文件的隔离夹具下，对照“下载规划后目标被抢先创建”应报失败且保留原字节、正常取消应只清理本次部分文件；上传另用可控 SFTP 服务器注入临时名碰撞，验证失败不删他人远端文件。Android 先区分本地文件路径与 SAF 目标，再分别测已存在目标/拒绝删除提供方；iOS、macOS、Linux 对照各自下载与上传路径。没有真实第三方 Android 文档提供方负向、外部进程高频替换路径或五端同候选真机结果。
