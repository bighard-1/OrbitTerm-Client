# SSH 二次验证专项验收记录

日期：2026-10-10。关联总台账 `SEC-02` / `SEC-03` / `SSH-MFA-DEVICE-01`。最初的源码修复和回环测试只改客户端与共享核心，没有更新线上服务或操作真实账户资产；后续真实 Debian 测试资产的尝试另记于本文末尾，不覆盖初始结论。

## 问题与目标

已报告症状：SSH 服务器在密码或私钥通过后、进入命令行前要求一次性验证代码；旧客户端双击资产后既不显示验证码入口，也未形成已连接会话。SSH 的 `keyboard-interactive` 属于客户端与 SSH 服务器之间的认证步骤，不依赖 OrbitTerm 业务服务端新接口。

目标：共享核心在明确的无回显验证码提示上返回稳定的 `ssh_second_factor_required`，标出目标机或跳板机；五端弹出遮蔽输入后，仅在同一次连接重试时传入对应跳的代码。存储的 SSH 密码不得作为验证码提交。未知提示、安全问题、回显提示及多轮超界一律不自动填答，也不把服务器原始提示送入 UI。

## 五端后续对照脚本

固定同一源码提交、原生库 SHA、包签名和隔离 SSH 测试主机策略，分别记录平台/构建/认证方法/跳数、是否弹窗、结果类别和会话是否实际打开；不记录验证码、密码、私钥、完整主机地址或原始网络报文。

1. 密码＋验证码：首次连接应在第一因子后明确弹出“目标服务器”验证码；正确代码打开终端，错误代码失败且不无限弹窗。重复点击、取消、切后台/断网均不得静默连接或保存代码。
2. 私钥＋验证码：禁用密码回退也应可完成第二因子；普通错误私钥仍需失败关闭。主机密钥首次信任、变更、拒绝时，验证码不得绕过既有信任门禁。
3. 跳板机＋目标机：仅跳板机要码、仅目标机要码、两者分别要码都要测；代码不得错投另一跳。两跳均要码时，第二次连接必须带上本次流程中的第一跳代码；重复同跳挑战失败。
4. 未知安全问题、带回显提示、超过受支持轮数及服务器不提供交互式方法：不自动提交持久 SSH 密码或此前代码，显示可解释的认证失败。业务服务端同步、资产明文和最近删除/墓碑不因连接失败发生变化。
5. 结束后检查客户端日志、崩溃报告、诊断与本地数据库/偏好设置/同步负载中没有代码明文。这里的实现是“流程内临时持有、不持久化/不同步”，不宣称通用内存零化。

Windows/Android 真机就绪后优先执行 1–5；Apple/Linux 也必须用真实 OTP 主机补齐。所有首次失败独立追加，成功重跑不得覆盖失败。正式验收关闭条件是五端在固定候选构建上均完成对应平台的真实交互，且错误码、取消、主机密钥和敏感数据检查通过。

## 2026-10-10 真实 Debian 资产首次尝试与暂停

用户提供自有 Debian 测试主机并授权加入专用测试账户。本文仅记录代号 `OT-TOTP-Debian-QA-20261010`；不记录账号、密码、完整地址、实时验证码或原始请求。Linux 隔离 GUI 使用旧 QA 候选 `6e62d9c` / SHA-256 `b42851faf2cc3e3c070f69458b43ba9870b3eaab3daa22c826b73135be2f5697`。新建资产选择“随账户同步”，UI 出现“同步”标记且同步状态健康；尚未由另一客户端或服务端脱敏修订独立证明云端回拉。既有 RDP 资产未修改，先前回环夹具仍为“仅此设备”。

首次连接弹出 ED25519 Host Key 确认。Linux 开发机扫描、macOS 隔离 known_hosts 及客户端弹窗显示同一指纹；这只是通过当前网络路径观察的一致性（首次使用信任），**不是带外身份核验**。信任后连接进入“认证中”，最后标签为“失败”，没有验证码弹窗、没有终端会话。旧 GUI 的错误状态标签虽写入脱敏诊断，却未挂载到可见组件树，因而用户只看到失败标签。脱敏诊断记录 `ssh_auth_failed` / `authentication_failed`；不保存诊断原文和资产地址。

为区分客户端 OTP 路径与主机第一因子问题，Linux 开发机和 macOS 本机各用标准 SSH 客户端进行**一次**受控密码验证。主机初始仅声明 `publickey,password`；两处均在输入用户提供的密码后返回 `Permission denied (publickey,password)`，未出现后续验证码提示。用户确认其常用客户端当前也无法凭这些信息进入单独验证码步骤，并要求先暂停，随后由其重置测试机登录方式。本次不再重试认证，不设置/上传密钥、不改 SSH/PAM/TOTP 配置，也没有获得或提交任何实时验证码。此失败不能证明客户端 OTP 功能有缺陷或已经通过。

发现后修复 Linux 工作区：把原先只供诊断读取的连接状态标签挂到可见页脚；活动 SSH 会话失败时展示明确失败页；对 `ssh_auth_failed` 给出稳定、可解释且不含凭据的文案。源码提交 `4cce231`。本地 `cargo fmt --all --check`、`git diff --check` 通过；Ubuntu 独立检出 `cargo check -p orbitterm-linux --locked` 与 `cargo build -p orbitterm-linux --locked` 通过，新 Debug 二进制 SHA-256 `dd5aabd3ee374e85d07d2821627eb796f5e7a6a5285cb0bab263819b34616df7`。首次从 Ubuntu 非登录 shell 直接运行 `cargo` 报未找到命令，随后用明确用户 Cargo 路径构建通过；保留为环境失败。**新二进制未安装或进行 GUI 复测**，不能把编译通过写成错误页已在 GUI 验收。

收到暂停指示后，精确向本次隔离 QA 应用、Openbox、Xvfb 发送 TERM 并核实退出；原有 Linux Flatpak 进程仍运行。隔离账户数据保留供用户重置后续测，不执行远端清理或永久删除。下一步须由用户确认测试机已恢复可登录，再以系统 SSH 验证密码后是否确实出现独立 TOTP 提示；若委托我设置 TOTP，先保留可恢复的认证路径，再做隔离 GUI 正确/错码和重连验收。Android/Windows 同候选真机对照第一因子失败原因是否可见、验证码是否只在服务器真正挑战时出现及敏感信息不落盘。`SSH-MFA-DEVICE-01` 与五端验收仍开放。
