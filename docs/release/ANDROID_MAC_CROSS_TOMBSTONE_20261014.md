## 执行与证据级别

1. **源码/自动化**：本节未新增源码修复。`4fd335d` 的本地 Android 完整 Release 门禁、QA 单测与 QA 构建结果见[总台账](FIVE_PLATFORM_FIX_AND_REGRESSION_LEDGER.md)。本节跨端结果不是自动化测试。
2. **隔离 GUI**：Mac QA 通过“添加服务器”保存虚构资产并显示同步成功及配置 ID。其“保存并连接”随后因文档保留地址不可达而报“网络暂不可用”；关闭失败会话标签后，资产仍已保存。此连接失败保留，不当作真实 SSH 故障。
3. **Android 真实设备**：K60 的 QA 资产页自动出现专用分组；展开后核对到同名虚构资产，手动同步后仍在。K60 仅在该资产编辑页执行可恢复删除，确认弹窗说明将移入最近删除并移除本机凭据。删除后专用分组消失，原两个测试分组仍在；“最近删除”可见精确同名条目，未执行永久删除。
4. **跨端接收与不复活**：K60 删除并触发同步后，Mac QA 第一次手动同步移除该分组和资产，第二次同步仍不存在；K60 再次手动同步也未复活。K60 强制结束并重开 QA 后先要求主密码，解锁后活动列表仍无该资产，原两个测试分组仍在。这是 **Mac 创建 → K60 接收并软删除 → Mac 接收墓碑** 的在线 GUI 交叉证据。
5. **恢复失败保留与 Mac 对照**：在 K60“最近删除”尝试恢复该条时，第一次扩展坞 ADB 中断，结果不确定；后续尝试后，GUI 明确显示“操作未完成，请检查网络、登录状态和主密码。操作未完成，当前删除记录仍可查看。”，条目仍在最近删除，Mac 再同步也未见恢复。K60 本轮恢复**失败**，不能用 ADB 返回码将其记为成功。随后在 Mac QA 的同一条最近删除记录点击“恢复”，GUI 显示“成功：资产已恢复”，活动分组和资产重新出现；再仅对该虚构资产执行可恢复删除，GUI 显示“已同步删除 1 条云端资产，可在最近删除中恢复”。这证明同一资产的服务端恢复路径至少可由 Mac QA 完成，但尚不能定位 Android 失败是在本地前置校验、传输、服务端冲突还是恢复后的本地写入。未做断网交叉、最终删除、iOS/Linux/Windows 同轮交叉或五端完整验收。

源码核查补充：Android 最近删除列表与恢复入口均取规范化资产 UUID，解密后的跨端配置在 `PortableServerConfig.validate()` 中转成小写；因此曾怀疑的 Apple 大写 UUID 与恢复处字符串比较不一致，**不足以解释本次失败**，未据此改码。现有通用错误文案不暴露失败阶段，后续须以脱敏阶段诊断或稳定触控复测确定根因。

后续找到高可信根因候选：Mac 用毫秒级 `Int64` 生成向量时钟，服务端按 `int64` 比较且恢复要求提交时钟严格更新；旧 Android `SyncVectorClock.decode()` 使用 `intOrNull`，会静默丢掉超出 32 位范围的 Mac 分量。删除路径允许并发时钟合并，所以删成功不能证明恢复也可用。Android 已将解析与递增改为 64 位，并新增保留 Mac 毫秒分量的回归测试；**这仍是源码/自动化证据，不改变上述旧 QA 真机恢复失败记录，新包复测前不记为修复验收通过**。

修复候选构建与安装：`SyncVectorClockTest` 定向 QA 单测通过；完整 Android Release 门禁 417 个任务通过。新独立 arm64 QA APK SHA-256 `c203c6e75581c5f3bc746d6b140345fe8845870e6b1d47dfcd67adf678ad41dd`，`assembleQa` 231 个任务成功；核实应用 ID 仍为 `com.orbitterm.android.qa`、桌面名“OrbitTerm QA”、arm64 ABI 且 APK 签名验证通过。K60 上 `adb install -r` 返回 `Success`，仅表示**新版包覆盖安装成功**；新版“恢复”GUI 结果待真机操作确认，不能因安装成功改写旧失败。

远程复测尝试：用户不在手机旁，授权我自行查看。扩展坞 ADB 一度显示已授权且可短暂唤醒 K60，但随后界面转储/截图传输不稳定；屏幕关闭时所得截图为全黑，无法可靠定位 QA 恢复按钮。**未点击新版的恢复、未修改任何资产**，因此新版恢复结果仍待验。已移除本次设备端临时 XML/截图与本机临时目录，并向手机发送锁屏指令；这次传输失败保留，不冒充功能失败或通过。

## 同日实体 K60 续验与反馈修复

用户回到 K60 旁后，在已安装的 64 位向量时钟 QA 包中仅对 `OT-K60-Cross-20261014` 点“恢复”：该条从最近删除消失并回到活动列表，故本轮**恢复功能通过**；但用户没有看到任何成功提示，属于独立的可用性缺口，不能说交互已通过。Mac 独立 QA 手动同步两次，活动列表确实重新出现同一虚构资产。Mac 随后只软删除该条，界面确认云端删除已同步；K60 用户手动同步两次，报告活动列表消失、最近删除可见。这证实一次**在线 K60 恢复 → Mac 接收 → Mac 删除 → K60 接收墓碑且不复活**。本轮未做离线、永久删除、同版签名或五端完整验收，原先的 K60 失败仍留在上文。

反馈缺口的源码检查：Android 成功/错误提示原来置于“最近删除”可滚动列表末尾，而恢复后该行立即消失；列表有多条记录时提示可能出现在当前视口之外。后继修复仅将该反馈移入固定标题区，不更改恢复请求或删除契约。`testQaUnitTest` 与 `assembleQa` 成功（241 项：15 执行、226 up-to-date）；完整 Android Release 门禁通过（417 项：29 执行、388 up-to-date）。新独立 arm64 QA 包 SHA-256 `c4d3f283dc5b70f23e51936a0795c4982f4b7fa7e3a26702a531084176c69e5a`，覆盖安装 K60 返回 `Success`，不是正式签名包。用户在该新包上对同一虚构资产再次点恢复，**确认“资产已恢复”提示可见、资产回到活动列表**；Mac QA 随后同步收到该资产，再仅软删除并显示云端删除已同步。K60 手动同步两次后确认活动列表消失、最近删除可见、未复活；旧包的无提示及恢复失败继续保留。

## SSH 主机身份安全阻断

真实 Debian 测试主机当前在 K60 弹出的 ED25519 指纹与 Mac 旧受信记录不同；同时点网络扫描与 K60 所见一致，但这不是主机侧独立身份证明。用户提出可先点确认并按连接结果验证；本轮没有这样做，因为密码或 TOTP 可能在身份尚未核实前发送给错误端点，且“能登录”本身无法解释旧指纹差异。用户目前暂不能从可信主机控制台核对。真实 SSH 二次验证测试继续暂停；之后应在主机控制台核对主机公钥指纹，查明是否曾合法重装/轮换，确认后再更新受信记录，不通过降低 Host Key 校验绕行。
